# Sciencetopia 关系数据存储指导原则

## 1. 目的

Sciencetopia 采用 **SQL + Neo4j 混合架构**。

为避免数据定义混乱、双写失控和查询边界模糊，所有“关系”必须按其业务性质进行分类，并遵循统一的存储原则。

本文件用于指导：

* 哪些关系只存 Neo4j
* 哪些关系必须存 SQL
* 哪些关系需要同时出现在 SQL 与 Neo4j 中
* 如何在双库场景下保持清晰的数据边界

---

## 2. 总体原则

### 2.1 三类关系

Sciencetopia 中的关系分为三类：

#### A. 纯图关系

主要用于图遍历、邻接发现、路径搜索、知识网络展示、推荐等。

**存储原则：只存 Neo4j。**

#### B. 业务关系事实

本身就是业务世界中的事实，通常涉及状态、角色、进度、审计、约束、后台管理等。

**存储原则：存 SQL。**

#### C. 既是业务事实又需要图查询的关系

既需要作为正式业务数据管理，又希望在图中参与遍历、推荐、关联探索等。

**存储原则：SQL 主存，Neo4j 投影。**

---

## 3. 判断标准

判断一条关系该放在哪里，不看它“像不像边”，而看它承担的职责。

### 3.1 属于“纯图关系”时

若一条关系满足以下特征，则应归为纯图关系：

* 主要用于图谱展示、多跳遍历、关联发现或推荐
* 不承载独立业务状态
* 不需要角色、进度、审核、审计等附加属性
* 不需要强事务约束
* 即使短暂缺失，也不会造成核心业务事实错误

**结论：只存 Neo4j。**

### 3.2 属于“业务关系事实”时

若一条关系满足以下特征，则应归为业务关系事实：

* 它本身就是正式业务记录
* 带有 role、status、progress、createdAt、updatedAt 等属性
* 需要唯一性约束、外键约束、审计或后台 CRUD
* 需要稳定参与事务逻辑
* 需要被列表页、后台、权限系统或统计系统直接使用

**结论：存 SQL。**

### 3.3 属于“双存关系”时

若一条关系同时满足以下两点，则应双存：

* 它本身是业务事实，必须在 SQL 中管理
* 它在图查询中也有明确价值

**结论：SQL 主存，Neo4j 投影。**

---

## 4. 存储规则

### 4.1 纯图关系

这类关系只保存在 Neo4j 中。

典型用途：

* 知识节点之间的语义连接
* 标签与主题之间的图结构
* 前置依赖关系
* 相似性、延展性、关联性关系
* 用于推荐与探索的边

实现要求：

* 不为其额外建立 SQL 镜像关系表
* 不将其作为核心事务数据使用
* 不依赖其承担后台业务状态管理职责

### 4.2 业务关系事实

这类关系应在 SQL 中以关系表形式存在。

典型特征：

* 有独立业务含义
* 有明确生命周期
* 有附加属性
* 需要约束和审计

实现要求：

* SQL 是唯一主事实来源
* 业务写入和状态变更以 SQL 为准
* 不允许仅在 Neo4j 中维护此类关系

### 4.3 双存关系

这类关系在 SQL 中存主事实，在 Neo4j 中存图投影。

实现要求：

* SQL 为 source of truth
* Neo4j 中只保存图查询所需信息
* Neo4j 投影应由 SQL 数据同步生成
* 不允许业务代码绕过 SQL 直接把 Neo4j 作为主写入口

---

## 5. 同步原则

对于双存关系，必须遵循以下原则：

### 5.1 单一主写入口

所有业务写入先进入 SQL。

### 5.2 Neo4j 是投影层

Neo4j 中的对应关系用于图查询、图谱展示、推荐与遍历，不承担主业务真相职责。

### 5.3 不允许无规则双写

不得在业务代码中将 SQL 与 Neo4j 视为两个平级主库并随意直接双写。

### 5.4 可重建

Neo4j 中的投影关系应可根据 SQL 主数据重新生成。

---

## 6. 查询原则

### 6.1 SQL 负责

以下查询优先使用 SQL：

* 后台管理
* 事务型业务查询
* 权限、角色、状态判断
* 进度与审计查询
* 列表页和结构化筛选

### 6.2 Neo4j 负责

以下查询优先使用 Neo4j：

* 多跳遍历
* 图谱展示
* 路径搜索
* 邻居发现
* 推荐与关系扩展

### 6.3 双存关系的读取

对于双存关系：

* 涉及业务事实判断时，读 SQL
* 涉及图结构遍历时，读 Neo4j

---

## 7. 常见反模式

以下做法应避免：

### 7.1 所有关系都双存

把所有 Neo4j 边再完整复制到 SQL，会造成：

* 数据定义重复
* 一致性维护困难
* 双写复杂度上升
* 查询边界模糊

### 7.2 两边都当主库

同一关系既允许 SQL 直接写，又允许 Neo4j 直接写，会导致主真相来源不明确。

### 7.3 用 Neo4j 承担事务业务事实

当一条关系本质上属于业务记录时，不应只存在于 Neo4j 中。

### 7.4 用 SQL 机械镜像纯图边

若某条边仅用于图结构遍历，则没有必要额外建 SQL 关系表。

---

## 8. 推荐落地方式

在具体设计中，应为每一种关系建立分类表，并明确以下字段：

* 关系名称
* 关系类型（纯图关系 / 业务关系事实 / 双存关系）
* SQL 是否存储
* Neo4j 是否存储
* 主事实来源
* 同步方向
* 主要查询用途

建议在系统设计阶段逐条登记，而不是由开发过程中临时决定。

---

## 9. 最终原则总结

Sciencetopia 的关系存储遵循以下核心原则：

* **纯图关系 → 只存 Neo4j**
* **业务关系事实 → 存 SQL**
* **既是业务事实又需要图查询 → SQL 主存，Neo4j 投影**

一句话概括：

**SQL 存业务事实，Neo4j 存图结构；重叠部分允许存在，但必须有主次。**
